# CR095 provider counterproposal for v4.7.3

For Adele and the CR095 authors. Proposed acceptance wording for flagged pits, supplementing the location-based revision to R1 and R2.

1. **Explicit return.** After a successful canonical write, the exact process holding the ticket writes `Returned|Originator|ClaimedAtUtc|LastWriteAtUtc|LastWriterMachine` to `Master.flag`. Verify on disk that the held turn has ended, the originator identifies the releasing machine, subscriber and PID, and the write timestamp records completion. A process that only publishes change files cannot release another writer’s ticket.
2. **Local turn-taking.** Start two independent processes A and B on the same host against the same local flagged pit. While A holds a valid ticket, B cannot write the canonical file. After A writes and returns the ticket, immediately retry with A while B is idle. A must be refused during its cooldown even with no other visible claimant. Pending edits follow the change-file path. During that same window B must be able to claim the available ticket and write immediately with zero propagation wait.
3. **Expiry.** In a separate case, let A return the ticket and leave it available. A is ineligible before its deadline and eligible at or after it. Reopening the same pit in the same process must preserve the cooldown. Calculate the deadline from write completion plus the effective `SyncPitDurationSeconds + BufferSeconds`. Document the effective local values and their source, including fallback when no timing file applies.
4. **Cloud fairness.** Retain CR090’s releasing-machine cooldown. After A returns a cloud ticket, another PID on A’s machine is also ineligible during that window. An eligible remote winner still serves its CR090 propagation wait and rechecks ownership before writing, even if only its own flag is visible.

The cooldown governs eligibility to claim. The propagation wait governs when a winner can write. A rejected retry returns promptly, and a different local winner serves zero propagation wait. The returned record identifies the last owner until the next claim replaces it with a held record identifying the new owner.
