# CR014 Test Concept — PitsCommand/IorgCommand Wrapper Testing

**Related CR**: CR014 — Typed CLI Command Wrappers
**Status**: Accepted by RAIkeep Principal as CR014 testing guidance
**Purpose**: Define the testing strategy for CLI command wrappers (`PitsCommand`, `IorgCommand`) in OsLib

---

## 1. Design Philosophy

The wrapper's responsibility is narrow and transport-focused:

> **The wrapper transports the CLI conversation. The calling agent decides what the output means and how prominently to display it.**

The wrapper should NOT:
- Interpret warnings and errors
- "Helpfully" handle process outcomes
- Duplicate the domain-level test suite of `pits` or `iorg`

The wrapper SHOULD:
- Accept declared tool parameters
- Convert them to correct CLI argument vectors
- Preserve ordering, quoting, empty values, repeated values, special characters
- Execute the CLI safely
- Capture `stdout`, `stderr`, and exit status
- Return all three to the agent caller without interpreting the message
- Surface enough metadata for the caller to decide UI display

---

## 2. Test Layers

### **Layer 1: Argument-Forwarding Tests**
- **Goal**: Verify exact parameter passthrough
- **Method**: Use a fake `pits`/`iorg` executable that records exactly what it received
- **Test**: Given input arguments, verify the wrapper forwards them without modification, reordering, or sanitization
- **Edge cases**:
  - Empty arguments
  - Arguments with spaces
  - Arguments with special characters (`"`, `'`, `\`, `$`, `;`, `&`, `|`, `<`, `>`, `` ` ``)
  - Arguments starting with `-` (options vs. positional)
  - Repeated arguments
  - Environment variable expansion interference

### **Layer 2: Output-Capture Tests**
- **Goal**: Verify stdout/stderr/exit status are captured faithfully
- **Method**: Fake commands emit various output patterns
- **Test patterns**:
  - Normal output (success messages)
  - Warnings only (stderr, exit code 0)
  - Errors only (stderr, exit code non-zero)
  - Mixed stdout/stderr (interleaved output)
  - Unicode characters in output
  - Very long output (boundary conditions)
  - No output (empty stdout/stderr)
  - Exit code 0 with no output
  - Non-zero exit codes with meaningful messages

### **Layer 3: Exit-Code Tests**
- **Goal**: Verify exit codes are returned, not swallowed
- **Test**:
  - Zero exit code → `"succeeded": true`, `"exitCode": 0`
  - Non-zero exit code → `"succeeded": false`, `"exitCode": <n>`
  - Exit codes are preserved exactly, not mapped to generic wrapper errors
  - Cancellation tokens respected and reflected in exit behavior

### **Layer 4: Permutation/Property Tests**
- **Goal**: Cover the argument grammar comprehensively without testing every permutation
- **Method**: Define the argument grammar and generate representative combinations, especially **pairwise combinations** of options
- **Explicit regression cases**: Add whenever a real forwarding bug is discovered
- **Test matrix** (representative, not exhaustive):
  - Optional arguments present/absent
  - Repeated arguments
  - Empty string arguments
  - Arguments containing spaces
  - Arguments containing quotes (single, double)
  - Arguments containing Unicode characters
  - Arguments beginning with `-` (distinguishing options from values)
  - Unusual ordering (options before/after positional arguments)
  - Mixed argument types in single invocation

**Note**: "I would not literally test every permutation. That quickly becomes mathematically unmanageable and provides diminishing returns. Instead, define the argument grammar and generate representative combinations, especially pairwise combinations of options."

### **Layer 5: Failure Tests**
- **Goal**: Verify wrapper behavior when things go wrong
- **Test cases**:
  - Executable missing from PATH → wrapper failure, not silent failure
  - Permission denied → wrapper failure with appropriate exit code
  - Timeout → cancellation handled gracefully, exit status returned
  - Cancellation during execution → clean exit, status returned
  - Malformed wrapper input → validation error, no process started
  - Invalid argument combinations → CLI behavior (error/warning output returned to caller, not swallowed)

### **Layer 6: Live Smoke Tests** (Minimal Set)
- **Goal**: Confirm the wrapper can invoke real CLIs
- **Test**:
  - Real `pits` CLI invocation (basic commands only)
  - Real `iorg` CLI invocation (basic commands only)
  - **Do NOT** try to validate every command's actual result
  - Confirm the wrapper structure works end-to-end with real executables
  - Use as regression guard, not comprehensive test suite

## 3. Expected Result Shape

```json
{
  "exitCode": 2,
  "succeeded": false,
  "stdout": "",
  "stderr": "Warning: ...\nError: ...",
  "timedOut": false
}
```

**Fields**:
- `exitCode`: Exact exit code from the CLI process (preserved, not mapped)
- `succeeded`: Boolean — `true` only when exit code is 0
- `stdout`: Raw stdout capture (may be empty)
- `stderr`: Raw stderr capture (may contain warnings, errors, or be empty)
- `timedOut`: Boolean — whether the operation timed out

**Important**: The wrapper returns all three values (`exitCode`, `succeeded`, `stdout`, `stderr`) without interpreting what they mean. The calling agent decides.

---

## 4. Agent-Facing Tool Design

> **For an agent-facing tool, I would also return the original `argv`—possibly redacted if secrets are possible—because it makes debugging and auditability much easier.**

**Design decision**: The wrapper should avoid "helpfully" interpreting warnings and errors. It should distinguish:

- **Wrapper failure**: Unable to start or control the process
- **CLI result**: The process ran and returned output/status

This preserves the division of responsibility:
- **Wrapper**: Transports the CLI conversation
- **Calling agent**: Decides what the output means and how prominently to display it

---

## 5. Acceptance Criteria for CR014_test-concept

This test concept is complete when:

1. ✅ Argument-forwarding tests verify exact parameter passthrough (no modification, reordering, or sanitization)
2. ✅ Output-capture tests cover normal output, warnings, errors, mixed stdout/stderr, Unicode, long output, and no output
3. ✅ Exit-code tests verify nonzero exit codes are returned—not swallowed or converted into vague wrapper errors
4. ✅ Permutation/property tests define the argument grammar and generate representative combinations, especially pairwise combinations of options
5. ✅ Failure tests verify wrapper failures (missing executable, permission denied, timeout, cancellation, malformed input) are surfaced correctly
6. ✅ Live smoke tests confirm the wrapper can invoke real `pits` and `iorg` CLIs without validating every command's result
7. ✅ Result shape includes `exitCode`, `succeeded`, `stdout`, `stderr`, `timedOut` fields
8. ✅ Wrapper distinguishes between wrapper failure and CLI result, neither interpreting the output
9. ✅ Original `argv` is returned (possibly redacted if secrets possible) for debugging and auditability
10. ✅ Tests are structured in layers (1-6 above), with Layer 4 using pairwise generation rather than exhaustive permutation testing

## 6. Implementation Notes

### **5.1 Wrapper API Surface**
The wrapper class (e.g., `PitsCommand`, `IorgCommand`) should inherit from or compose with `CliCommand` and expose:
- `RunAsync(arguments)` → `Task<RaiSystemResult>`
- Properties: `ExecutableName`, `PackageName`, `IsAvailable`, `TryResolveExecutable`
- Result shape as defined in Section 3 above

### **5.2 Test Placement**
```
RAIkeep/OsLib.Tests/
  RaikeepCliCommandTests.cs

RAIkeep/PitSeeder/pits.Tests/
  CliSubcommandTests.cs        # minimal real pits smoke invocation

RAIkeep/ImgSeeder/ImgSeeder.Tests/
  CliSubcommandTests.cs        # minimal real iorg smoke invocation
```

### **5.3 Integration with CR014**
- CR014 defines and implements the public wrappers.
- CR014.1 defines the required testing strategy for those wrappers.
- Capture-double tests run in OsLib; real-CLI smoke checks run in the owning CLI
  projects and do not duplicate domain behavior.
- No eighth package or umbrella acceptance harness is introduced.

---

## 7. Resolved Decisions

1. Wrapper names are `PitsCommand` and `IorgCommand`, both extending
   `CliCommand`.
2. `RaiSystemResult` remains the shared result type and exposes command,
   argument-vector, output, error, exit, success, and timeout state.
3. Arguments are returned exactly. The wrapper does not guess which
   domain-specific values are secrets; callers decide what they log.
4. Representative combinations are explicit tests; no additional pairwise
   generation dependency is introduced.
5. The real-CLI smoke scope is `--version` through each wrapper and the actual
   managed CLI assembly.
6. CR014.1 is an accepted testing addendum to CR014 for v4.2.2.
